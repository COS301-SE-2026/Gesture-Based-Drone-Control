<br/>

Control a drone with your hands. Our system uses real-time computer vision to recognize gestures and translate them into flight commands, with calibration and safety checks built in. Fly in a simulator, compete in gesture-controlled minigames, challenge yourself in testing environments, or switch to a keyboard, gamepad or on-screen controls. From learning the controls to practising flight, the project brings drone interaction into a more intuitive, accessible and interactive experience for pilots of all skill levels.

### Gesture vocabulary

The rule-based recognizer classifies six gestures from MediaPipe's 21 hand landmarks for each finger raised, plus an `UNKNOWN` failure state for low-confidence or unmatched frames. Per-frame classifications pass through the `GestureStabilizer`, which takes the majority vote from a sliding window of frames.

### Calibration gate

Before any flight command is accepted, the user walks the calibration sequence once. This is a safety net that proves the pipeline can read *this* user's hand under *this* lighting. 

The sequence runs through each gesture, proceeding once the system is confident that a gesture is sufficiently recognised

### Hardware Communication

The system allows for seamless integration of more HIDs (Human-Interface Devices) and drones through the use of a unique two-way adapter. Each HID inherits from an abstract `InputAdapter` class, and each drone inherits from an abstract `DroneAdapter` class. 

This means that adding a new input method or drone implementation requires only one new file; and every existing implementation on the other side of the adapter is automatically guaranteed to work with no further configuration.

### API interface

Everything is mounted under the `/api` prefix. Interactive Swagger docs are served at `/docs` when the backend is running.

The project uses a monorepo structure that separates the frontend, backend, shared packages, and supporting services. 

It includes dedicated modules for computer vision, gesture recognition, drone control, input handling, telemetry, authentication, and database management. 

The repository also contains unit and integration tests, performance testing tools, project documentation, packaging configurations, and the library for Project AirSim, maintained as a submodule.

[![Node](https://img.shields.io/badge/Node.js-22-A4161A?style=flat-square&logo=node.js&logoColor=F5F3F4&labelColor=161A1D)](https://nodejs.org)
[![Yarn](https://img.shields.io/badge/Yarn-1.22+-A4161A?style=flat-square&logo=yarn&logoColor=F5F3F4&labelColor=161A1D)](https://yarnpkg.com)

<details>
<summary>Expand for comprehensive instructions to start developing</summary>

> This project uses [Taskfile](https://taskfile.dev/) as an OS agnostic alternative to Make. It's a really nice tool.

Note, **Python must be 3.11.** The workspace pins `>=3.11,<3.12` because MediaPipe and the AirSim clients have no wheels beyond it.

If uv is not installed, follow the official installation [instructions](https://docs.astral.sh/uv/getting-started/installation/).

```bash
brew install go-task              # macOS
sudo snap install task --classic  # Linux
winget install Task.Task          # Windows
```

<br/>

**Clone the repository**

```bash
git clone --recurse-submodules https://github.com/COS301-SE-2026/Gesture-Based-Drone-Control.git
cd Gesture-Based-Drone-Control
cp .env.example .env
```

If you already cloned the repository without its submodules, initialise them with:

```
git submodule update --init --recursive
```

<br/>

**Install Dependencies and Libraries**

```bash
task install
```

This creates a Python 3.11 virtual environment, installs the dependencies required by AirSim, synchronizes the Python workspace and installs the frontend dependencies with Yarn.

Configure the environment variables in .env before running the application. In particular, set the backend port and any simulator paths required by your setup.

<br/>

**Run the application locally**

```bash
task dev
```

This starts the FastAPI backend and the Vite frontend development server. The backend uses BACKENDPORT from the environment; the frontend runs from apps/frontend.

To run either component separately:

```
task backend-dev
task frontend-dev
```

The public landing page has its own development server:

```
task landing
```
<br/>

**Test**

```bash
task test           # everything: unit, integration, end to end
```

Or by layer:

```bash
task unit-test             # Frontend and backend unit tests
task backend-unit-test     # Backend and services tests
task frontend-unit-test    # Frontend unit tests
task integration-test      # Integration tests
task e2e-test              # End-to-end tests
```

<br/>

**Linting and formatting**

```bash
task lint    # Python linting, frontend linting and API contract validation
task fix     # Automatically fix supported Python and frontend formatting issues
```

<br/>

**Build the desktop app**

```bash
task build
```

The build stages the simulator and its Pixel Streaming signalling server, packages the backend with PyInstaller, and builds the Electron desktop application.

Simulator build requirements:

- Set SIM_SRC in .env to the simulator directory or archive used for staging.

- The simulator staging task supports Linux and macOS shell environments, as well as a separate Windows PowerShell script.

- The staged simulator must contain the expected Blocks project and Linux shipping binary where applicable. Check the platform-specific staging requirements before building.

To remove generated build output:

```
task clean
```
